# JARVIS 결과공유회 발표 대본 (발표 15분 + 질의응답 2분)

구성은 중간발표 흐름(1부 배경 → 2부 문제 → 3부 해결 → 4부 이후 플랜/스케일업 → 마무리)을 그대로 이어갑니다.
심사 항목(프로젝트형 정성): ① 목표달성도 ② 회사성장기여도 ③ 임팩트/확산성 ④ 산출물완성도 ⑤ 기타(난이도·실행가능성)
각 슬라이드 하단에 해당 심사 항목 배지가 있으며, 대본의 **[①~⑤]** 표시는 강조 지점입니다.

| 구간 | 슬라이드 | 시간 | 누적 | 주요 심사 항목 |
|---|---|---|---|---|
| 오프닝 | 1–2 | 0:30 | 0:30 | — |
| 1부 배경 | 3–4 | 1:40 | 2:10 | ② |
| 2부 문제 | 5–7 | 2:40 | 4:50 | ② ① |
| 3부 해결 | 8–16 | 8:20 | 13:10 | ④ ① ② ⑤ |
| 4부 스케일업 | 17–19 | 1:20 | 14:30 | ③ ② |
| 마무리 | 20 | 0:30 | 15:00 | ①~⑤ 요약 |

---

## 1–2. 표지 · 목차 (0:30)
안녕하십니까. 하나금융티아이 CoP **JARVIS** 팀입니다. 중간발표에서 "AIOps로 장애 대응 시간을 줄이다"라는 목표를 말씀드렸는데, 오늘은 그 결과를 배경, 문제, 해결, 스케일업 순서로 공유드리겠습니다.

## 3. 서비스가 복잡해질수록 복구 속도가 경쟁력 (0:50)
- MSA·클라우드 전환으로 장애 원인의 조합이 폭발적으로 늘었고, 이제 핵심 SLA는 MTTR, 즉 복구까지 걸린 시간입니다.
- 결제·이체·인증은 몇 분만 멈춰도 거래 실패와 민원으로 이어집니다.
- '장애가 없는 서비스'보다 '가장 빨리 복구하는 서비스'가 경쟁력입니다.

## 4. 장애 대응은 아직 개인의 경험에 (0:50) **[②]**
로그를 눈으로 확인하고, 과거 사례는 기억과 위키에 의존하며, 대응 결정은 경험치에 따라 달라집니다. 대응 지식이 시스템이 아니라 사람에게 쌓여 있어서, 담당자가 없으면 품질이 떨어지고 같은 장애도 매번 처음부터 조사합니다.

## 5. MTTR의 대부분은 '판단'에서 (1:00) **[②]**
탐지, 원인 파악, 대응 결정 같은 초기 대응(Triage)이 병목입니다. 실제 명령 실행은 짧고, 사람이 로그를 훑고 판단하는 시간이 MTTR의 대부분입니다. 그 결과 유사 장애 재조사, 담당자 부재 시 품질 저하, 다운타임, 온콜 번아웃이 생깁니다.

## 6. 판단을 AI에 맡길 때의 네 가지 벽 (1:00) **[②]**
P1 후속·반복 ERROR로 인한 알림 폭주, P2 근거 없는 LLM 추천, P3 잘못된 대상·중복 실행 같은 위험한 실행, P4 복구 미검증과 민감정보 유출. 빠르게 하려면 위험하고, 안전하게 하려면 느린 딜레마입니다.

## 7. 우리가 풀어야 할 질문 (0:40) **[①]**
"AI의 속도로 원인을 찾고, 사람의 통제 아래에서 검증된 복구까지 끝낼 수 있을까?"
이 질문에 답하기 위해 빠르게, 근거 있게, 안전하게, 끝까지라는 네 가지 원칙을 CoP의 목표로 세웠습니다. 지금부터 각 원칙을 어떻게 구현했는지 보여드리겠습니다.

## 8. 전체 파이프라인 (0:50) **[④]**
수집부터 복구 확인·학습까지 7단계 파이프라인입니다. 문제 4개에 핵심 기능 F1~F5로 답합니다. 앞의 네 가지 원칙이 각각 기능으로 이어집니다.

## 9. 실제 구현된 아키텍처 (1:00) **[④ ⑤]**
- 수집: log-generator의 장애 시나리오 20종을 Fluent Bit가 1초 주기로, 자원 지표는 Collector가 수집합니다.
- 분석: API가 마스킹 후 Redis Streams에 넣고 202를 돌려주면, Worker가 오류 탐지·사례 검색·LLM 추천을 수행해 Elasticsearch·Qdrant에 저장합니다. LLM을 끄면 결정론 추천으로 동작합니다.
- 실행·운영: 콘솔에서 승인하면 승인·실행 API가 조건을 검증하고, 등록된 Runbook 58개를 실행한 뒤 복구를 확인합니다.
- 서버 한 대(8GB·2vCPU)에서 상시 메모리 5.5GiB 상한으로 동작합니다.

## 10. F1 장애 집약 (0:50) **[④]**
오류 21종을 자동 분류하고, 후속 메시지 39개는 장애로 만들지 않으며, 300초 안의 반복 오류는 기존 분석을 재사용하고, 업무 영향으로 P1~P3 등급을 매깁니다. "로그 100줄이 아니라 장애 1건." — **빠르게**의 구현입니다.

## 11. F2 하이브리드 원인 분석 (1:10) **[④]**
중간발표에서 보여드린 Qdrant(의미) + Elasticsearch(키워드) 하이브리드 검색 위에 품질 게이트와 자원 가설 엔진을 더했습니다. LLM이 없어도 결정론 랭커로 추천이 유지되고, 근거가 부족하면 원인을 지어내지 않고 지표 근거가 있는 가설만 제시합니다. — **근거 있게**의 구현입니다.

## 12. 장애 20종 검증 (1:00) **[④ ①]**
중간발표 때 6종이던 시나리오를 20종으로 늘렸습니다. 각 장애마다 진단 스크립트와 우선순위가 매겨진 조치 Runbook이 연결되고, 20개 중 19개는 자동 연결, Rate Limit 1개는 수동 조치 등록으로 처리합니다. 자동 검사는 158개 중 157개가 통과했습니다(1개는 Docker 환경이 필요해 생략).

## 13. F3 승인 기반 실행 (1:00) **[④ ①]**
중간발표의 Next Step이었던 "운영자가 고르면 실행되는" 단계를 구현했습니다. 대상 선택 → 승인 → 서버의 8가지 조건 검증 → 실행 → MONITORING. 셸·exec는 쓰지 않고, 실행 기록으로 중복 실행을 막으며, 실패하면 이전 상태로 복원합니다. — **안전하게**의 구현입니다.

## 14. F4 복구 검증 · 학습 (1:00) **[④]**
명령이 끝나면 MONITORING, health와 업무 KPI를 2회 연속 확인해야 RESOLVED입니다. 운영자가 확정한 사례만 지식으로 쌓이는 플라이휠입니다. 덧붙여 저장·LLM 입력·응답 전 구간에서 민감정보를 마스킹하고, 외부 LLM을 끌 수 있는 스위치를 두었습니다. — **끝까지**의 구현입니다.

## 15. 기존 서비스 연계 · 업무 개선 (0:50) **[②]**
기존 로그, 운영 스크립트, 업무 API를 수정 없이 연결합니다. 인지·판단·조치·확인·기록 다섯 가지 업무가 Before/After처럼 바뀝니다.

## 16. 난이도 · 현업 적용 가능성 (0:40) **[⑤]**
분산 큐, 하이브리드 AI, 멱등 실행, 실시간 동기화를 서버 한 대 자원 안에서 풀었습니다. 도입은 쉽습니다. 명령 한 줄로 설치되고, 외부망 없이 동작하며, 업무 시스템을 바꾸지 않습니다.

## 17. 운영 데이터 학습으로 (0:30) **[③]**
중간발표의 이후 플랜을 단계로 구체화했습니다. Phase 2 운영 데이터·실 업무 KPI·권한·알림 → Phase 3 few-shot 고도화·재학습·SAFE/LOW risk부터 단계적 자동 실행 → Phase 4 그룹 공통 플랫폼.

## 18. 확산성 (0:30) **[③]**
CoP 팀 → 운영 조직 → 전사 → 그룹 관계사 순으로 넓힙니다. 사례 지식 공유, 같은 방식의 설치, 파일 등록만으로 끝나는 온보딩, 문서·자동 검사가 확산 장치입니다.

## 19. 확장 구조 · 성과 측정 (0:20) **[② ③]**
LLM·저장소·대상·오류 유형을 바꿔 끼우기 쉬운 구조이고, MTTR·노이즈·추천 채택률·재발률을 JARVIS가 이미 저장하는 이력으로 측정합니다.

## 20. 마무리 (0:30)
사람이 로그를 훑으며 하던 "이거 왜 터졌지?"를 JARVIS가 근거와 함께 먼저 답하고, 운영자는 승인 한 번으로 대응하고, 업무 지표로 복구를 확인합니다. 감사합니다.
