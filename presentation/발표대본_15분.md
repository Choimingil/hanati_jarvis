## 1–2. 표지 · 목차 (0:30)
안녕하십니까. 저희 CoP는 로그와 자원 정보를 스스로 읽고, 원인을 찾고, 운영자 승인 아래 복구까지 끝내는 장애 대응 에이전트 **Hanati Jarvis**를 만들었습니다. 배경, 문제, 해결, 스케일업 순서로 말씀드리고, 각 장에서 다룰 심사 항목은 화면 아래에 표시해 두었습니다.

## 3–5. 배경 (1:20)
- 금융 서비스는 24시간 무중단이 기본이고, 장애 대응 시간이 곧 서비스 품질입니다.
- 시스템은 API·DB·Redis·Kafka·외부 PG로 잘게 쪼개져, 장애 하나가 여러 곳에 오류를 남깁니다.
- 관측 도구는 충분하지만 "그래서 지금 무엇을 해야 하는가"를 알려주는 연결 고리가 없습니다.
- 장애 대응은 탐지 → 분석 → 조치 → 확인 4단계인데, 대부분의 시간은 원인 분석에 들어갑니다. 그렇다고 AI가 서버를 마음대로 재시작하게 둘 수도 없습니다. **[② 우리 조직의 실제 업무 문제]**

## 6. CoP 활동 목표 (1:00) **[①]**
- 그래서 저희는 네 가지 목표를 세웠습니다.
  - G1: 수집부터 복구 확인까지 하나의 서비스로
  - G2: 금융 빈발 장애 20종 이상을 자동 분석·추천
  - G3: 사람이 통제하는 안전한 조치
  - G4: 현업에 바로 써볼 수 있는 운영 수준
- 7월부터 10월까지 4개월 동안 5명이 99건의 커밋으로 진행했습니다. 목표별 달성 결과는 해결 파트 마지막에 보고드리겠습니다.

## 7–9. 문제 (1:50) **[②]**
- P1 알림 폭주: 핵심 오류 뒤의 후속 ERROR와 반복 오류가 각각 장애로 쌓여 진짜 원인이 묻힙니다.
- P2 경험 의존: 과거 사례 지식이 담당자 머릿속에만 있습니다.
- P3 위험한 조치: 엉뚱한 대상, 중복 실행, 이중화가 없는 상태에서의 재시작.
- P4 복구 미검증·정보 유출: 명령 성공을 복구로 오판하고, 고객 정보가 외부 LLM으로 나갈 위험이 있습니다.
- 문제 정의: "AI의 속도로 원인을 찾고, 사람의 통제 아래 검증된 복구까지 끝낼 수 있을까?" — 빠르게, 근거 있게, 안전하게, 끝까지.

## 10–11. 해결 개요 · 아키텍처 (1:10) **[④ 서비스 목적 전달]**
- 수집부터 학습까지 7단계의 닫힌 루프입니다. 문제 4개에 핵심 기능 5개로 답합니다(표의 F1~F5 ↔ P1~P4).
- Compose 한 번으로 뜨는 이벤트 기반 구조입니다. API는 마스킹 후 Redis Streams에 넣고 바로 202를 돌려주며, Worker가 분석해 ES·Qdrant에 저장합니다. 실행은 정책 기반 Agent가 맡습니다. **[⑤ 기술 난이도]**

## 12. F1 장애 집약 (0:40) **[④]**
오류 21종을 자동으로 분류하고, 후속 메시지 39개는 장애로 만들지 않으며, 300초 안의 반복 오류는 기존 분석을 재사용하고, 업무 영향에 따라 P1~P3 등급을 매깁니다. "로그 100줄이 아니라 장애 1건."

## 13. F2 하이브리드 원인 분석 (0:50) **[④]**
진단 스크립트 → Qdrant 유사 사례 Top-3 → LLM 추천 → 품질 게이트 → 자원 가설 엔진. LLM이 없어도 결정론 랭커로 추천이 유지되고, 근거가 부족하면 원인을 지어내지 않고 지표 기반 가설만 제시합니다.

## 14. F3 승인 기반 실행 (0:50) **[④]**
대상 선택 → 승인 → 서버 검증 → 실행 → MONITORING. 승인 시 서버가 ID·버전·만료, 대상 결합, 이중화, 분산 잠금 등 8가지 조건을 확인합니다. 셸·exec는 쓰지 않고, 실행 기록으로 중복 실행을 막으며, 실패하면 이전 상태로 복원합니다.

## 15. F4 복구 검증 · 학습 (0:40) **[④]**
MONITORING과 RESOLVED를 분리합니다. health와 업무 KPI(성공률·p95·거래 수)를 2회 연속 통과해야 해결로 봅니다. 운영자가 확정한 사례만 Qdrant로 승격해 지식이 쌓입니다.

## 16. F5 보안 · 거버넌스 (0:30) **[④]**
저장·LLM 입력·응답 전 구간에서 마스킹하고, LLM OFF 스위치를 두며, 승인·실행을 감사 기록으로 남깁니다. "보안팀이 '이렇게 쓰면 된다'고 말할 수 있는 구조."

## 17–18. 시연 (1:20) **[④ 핵심 기능을 직접 보여줌]**
/admin에서 시나리오 실행 → 장애 1건 생성·강조 → 상세에서 원인·사례·추천 확인 → 승인 후 실행 → 업무 복구 확인 → 다른 화면에 처리 완료가 동기화되는 것까지 보여드립니다. (라이브가 불안하면 녹화 영상으로 대체)

## 19. 기존 서비스 연계 · 업무 개선 (0:40) **[② 회사성장기여도]**
- 새 시스템을 하나 더 들이는 것이 아니라 기존 로그, 기존 운영 스크립트 58개, 업무 상태 API를 그대로 연결합니다. 업무 코드는 수정할 필요가 없습니다.
- 인지·분석·조치·확인·기록 다섯 가지 운영 업무가 각각 이렇게 바뀝니다(Before/After 표).

## 20. 목표 대비 달성도 (0:40) **[① 목표달성도 · ④]**
- G1~G3은 계획한 범위를 모두 달성했습니다. G4는 EC2 자동 배포, 자원 설계, 마스킹, 자동 검사 158개 중 157개 통과까지 핵심을 달성했습니다.
- 실제 거래 KPI 연동과 로그인/권한 관리는 운영 환경 정보가 필요해 Phase 2로 넘겼습니다. 솔직하게 구분해서 말씀드립니다.

## 21. 난이도 · 현업 적용 가능성 (0:30) **[⑤ 기타]**
분산 큐, 하이브리드 AI, 멱등 실행, 화면 간 실시간 동기화를 서버 한 대 자원 안에서 해결했습니다. 반면 도입은 쉽습니다. 명령 한 줄로 설치되고, 외부망 없이도 동작하며, 업무 시스템을 바꾸지 않습니다.

## 22–23. 스케일업 로드맵 (0:30) **[③]**
현재 단일 서버 PoC → Phase 2 실 업무 KPI·SSO/RBAC·알림 → Phase 3 K8s·Worker 수평 확장·사내 LLM → Phase 4 그룹 공통 AIOps 허브.

## 24. 임팩트 · 확산성 (0:40) **[③ 임팩트/확산성]**
CoP 팀 → 운영 조직 → 전사 → 그룹 관계사 순으로 확산합니다. 확산 장치는 네 가지입니다: 확정 사례 지식베이스 공유, 동일하게 설치할 수 있는 표준 패키지, 파일 등록만으로 끝나는 온보딩, 문서와 자동 검사.

## 25. 확장 근거 · 성과 측정 (0:30) **[② ③]**
포트·어댑터와 정책 파일 구조라서 LLM·저장소·대상·오류 유형을 바꿔 끼우기 쉽습니다. 도입 효과는 MTTR, 노이즈, 추천 채택률, 재발률로 측정하며, 모두 Jarvis가 이미 저장하는 이력에서 자동으로 계산됩니다.

## 26. 마무리 (0:30)
요약하면 목표 4개를 달성했고, 기존 업무와 연계해 개선했으며, 조직 전체로 확산할 수 있고, 핵심 기능을 직접 보여드렸고, 어려운 문제를 현장에 바로 놓을 수 있는 형태로 풀었습니다. AI의 속도로 찾고, 사람의 통제로 실행하고, 업무 지표로 끝까지 확인합니다. 감사합니다.
